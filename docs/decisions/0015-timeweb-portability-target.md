# ADR-0015: Timeweb как российский portability target

- Статус: принято
- Дата: 2026-09-01
- Владельцы: владелец продукта, архитектура Forme
- Заменяет: —

## Контекст

MVP работает в Sites поверх D1 и R2 без VPS. Для личного использования это удобно, но доступ к Cloudflare из российских сетей может быть нестабилен. Нужен российский целевой контур, который не требует ручного администрирования сервера и не создаёт новую зависимость доменной модели от конкретного провайдера.

## Критерии решения

- доступность и оплата из России;
- управляемый запуск приложения без администрирования VPS;
- стандартные PostgreSQL и S3 API;
- поддержка `pgvector` для будущего hybrid retrieval;
- резервное копирование и обратимая миграция;
- минимальные изменения application/domain слоёв.

## Рассмотренные варианты

1. Оставить только D1/R2. Минимум работы, но нет российского аварийного контура.
2. YDB Serverless + Object Storage. Экономичная serverless-модель, но собственный SDK и SQL-диалект увеличивают стоимость миграции.
3. Yandex Managed PostgreSQL + Object Storage + Serverless Containers. Полный управляемый стек, но для личного MVP сложнее по эксплуатации.
4. Timeweb App Platform + Managed PostgreSQL + S3. Стандартные протоколы, простой деплой и `pgvector` в одной управляемой БД.

## Решение

Timeweb принимается как первый российский portability target, а не как немедленная замена работающего production-контура:

- `D1 → PostgreSQL` через отдельные infrastructure adapters;
- `R2 → S3` через `SourceFileStore` и совместимый S3 adapter;
- `Sites/Worker → App Platform` через контейнерный HTTP runtime;
- semantic indexes → отдельные пространства `pgvector` для source chunks и approved claim versions.

Каноническая схема, application ports, evidence gates и LLM orchestration остаются provider-neutral. Миграция выполняется через экспорт, проверку количества и хешей, временную dual-read сверку и явный cutover. Dual-write до сверки запрещён.

## Последствия и риски

- приложение можно перенести без изменения научной доменной модели;
- PostgreSQL даёт стандартный путь к векторному поиску;
- потребуется отдельная реализация SQL-запросов и миграций под PostgreSQL;
- текущий Sites runtime не открывает raw TCP к внешней БД, поэтому переключение БД связано с переносом server runtime;
- перенос не начинается без автоматического D1/R2 export и restore drill.

## Проверка и пересмотр

Решение пересматривается после измерения доступности production из России, стоимости месячной нагрузки и размера корпуса. Готовность к cutover подтверждается восстановлением тестовой копии, сравнением row/object counts, content hashes и прохождением полного `npm run check` на PostgreSQL/S3 adapters.
