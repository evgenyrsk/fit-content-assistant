# ADR-0005: Provider-agnostic economy routing

- Статус: принято
- Дата: 2026-08-27
- Заменяет: частное MVP-предпочтение OpenAI Vector Stores в `RAG_ARCHITECTURE.md`

## Контекст

Пользователь выбрал provider-agnostic архитектуру и экономный режим без фиксированного денежного лимита. Научный контур не должен зависеть от встроенного поиска или хранилища одного LLM-провайдера.

## Критерии решения

- одинаковая доменная семантика при смене провайдера;
- строгие structured outputs;
- наблюдаемая стоимость и фактический route;
- минимальный контекст и лимиты по этапам;
- возможность сравнить провайдеры на одном eval-наборе.

## Рассмотренные варианты

- Один прямой провайдер: быстрее подключить, но создаёт lock-in.
- Только OpenRouter: удобная маршрутизация, но сохраняет зависимость от одного gateway.
- Внутренний порт и сменные адаптеры: немного больше кода, но сохраняет контроль Forme над evidence и retrieval.

## Решение

Оставить `LlmProvider` единственной application-границей. Реализовать прямой OpenAI Responses adapter и OpenRouter adapter. Model ids и capabilities задаются окружением. Economy profile ограничивает output и tool calls по stage; OpenRouter сортирует совместимые маршруты по цене и запрещает data collection на уровне запроса.

D1 остаётся канонической базой. Lexical и semantic retrieval реализуются через сменные индексы; OpenAI Vector Stores может быть одним adapter, но не архитектурным обязательством.

## Последствия и риски

- Нужны contract tests для каждого adapter.
- Capability конкретной модели нельзя выводить только из имени; она задаётся и проверяется конфигурацией.
- Без денежного лимита система ограничивает токены и число вызовов, но не обещает фиксированную месячную стоимость.

## Проверка и пересмотр

Primary/fallback выбираются после одинакового eval по качеству, задержке и реальной стоимости. Решение пересматривается, если поддержка нескольких adapters начинает ухудшать надёжность без измеримой пользы.
