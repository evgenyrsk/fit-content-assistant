# ADR-0003: Модульный монолит и контролируемые границы кода

- Статус: принято
- Дата: 2026-08-27
- Владельцы: Forme

## Контекст

MVP должен быстро развиваться, а научный и контентный конвейеры будут усложняться независимо. Один крупный UI-файл и общая папка интеграций создают риск скрытой связанности. Микросервисы сейчас добавили бы эксплуатационную сложность без измеримой пользы.

## Критерии решения

Простота MVP, тестируемость научных gates, сменяемость LLM-провайдеров, локальность изменений, возможность позднего выделения модулей и автоматическая проверка границ.

## Рассмотренные варианты

- Один слой компонентов и сервисов: быстро в начале, но плохо контролирует зависимости.
- Микросервисы: сильная физическая изоляция, но преждевременная сеть, деплой и согласованность данных.
- Модульный монолит: логические границы внутри одного deployable приложения.

## Решение

Использовать feature-модули для UI и Clean Architecture layers для домена: `domain ← application ports ← infrastructure`, с `app` как composition root. Cross-feature imports проходят через публичные entrypoints. Размеры файлов и функций, количество классов и базовая сложность проверяются автоматически.

## Последствия и риски

Изменения локализуются, адаптеры сменяемы, а будущий extraction получает естественные seams. Появляется больше небольших файлов и необходимость поддерживать публичные границы. Избыточная абстракция с единственной реализацией без ожидаемой вариативности запрещена.

## Проверка и пересмотр

Решение проверяется архитектурным скриптом, ESLint и code review. К выделению сервиса возвращаемся только при независимом масштабировании, безопасности, ownership или release cycle, которые нельзя разумно обеспечить внутри монолита.
