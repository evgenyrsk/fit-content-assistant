# Организация кода Forme

## Архитектурный стиль

Forme развивается как модульный монолит. Это сохраняет простую эксплуатацию MVP, но даёт явные границы, по которым отдельный модуль можно усложнить или вынести в сервис, когда появятся измеримые причины: независимое масштабирование, отдельный release cycle, изоляция данных или команды.

## Направление зависимостей

`app → feature UI → application use cases → domain`

`infrastructure → application ports → domain`

- `app/` — composition root: маршруты, сборка модулей и dependency injection. Здесь нет бизнес-правил.
- `features/<name>/` — пользовательский сценарий и его UI. Внешний код использует только публичный `index.ts` модуля.
- `features/shared/` — только действительно общие presentation-типы и демо-данные; не место для бизнес-логики.
- `lib/domain/` — сущности, value objects, политики и инварианты без React, SDK, HTTP и базы данных.
- `lib/application/` — use cases, оркестрация и узкие порты внешних зависимостей.
- `lib/infrastructure/` — адаптеры OpenAI/OpenRouter/RouterAI, D1, vector store и внешних API.
- `styles/` — стили по поверхности или ответственности; порядок импорта задаётся в `app/globals.css`.

Domain не импортирует application, infrastructure или UI. Application не импортирует infrastructure или UI. Infrastructure реализует application ports. Связка конкретных реализаций происходит только в composition root.

## SOLID как рабочие правила

- **Single Responsibility.** Один модуль, файл, компонент, hook или класс имеет одну причину измениться. Состояние интерфейса живёт рядом со своим feature, а не в глобальном god-component.
- **Open/Closed.** Новые провайдеры, источники, оценщики и форматы добавляются реализацией порта или стратегии, а не разрастанием общего условного блока.
- **Liskov Substitution.** Любой adapter обязан пройти один contract/conformance-набор; fallback не может менять смысл результата.
- **Interface Segregation.** Порты узкие и называются по возможности клиента. Не создаём универсальные интерфейсы с методами «на будущее».
- **Dependency Inversion.** Use case зависит от порта, а SDK-адаптер — от этого порта. Vendor types не пересекают границу infrastructure.

Классы используются только когда есть состояние или жизненный цикл, которые действительно выигрывают от инкапсуляции. По умолчанию предпочтительны чистые функции, явные типы и композиция. Один файл может экспортировать не более одного класса.

## Ограничения размера

- Цель: до 200 строк на исходный файл; hard limit: 250.
- Цель: до 80 строк на функцию, React-компонент или hook; hard limit: 120.
- Не более одного класса в файле.
- Сложность функции — не выше 10, вложенность — не глубже трёх уровней, не более четырёх позиционных параметров.
- Большой JSX делится по пользовательским сценариям, а не на бессмысленные визуальные обёртки.
- Большая схема или набор данных делится по доменной принадлежности. Generated artifacts в эти лимиты не входят.

Правила проверяются `npm run architecture` и ESLint внутри общего `npm run check`.

## Имена и публичные границы

- Имена отражают предметную область: `claim-review`, `source-assessment`, `content-brief`, а не `utils` или `helpers`.
- Запрещены файлы-свалки `utils.ts`, `helpers.ts`, `common.ts`.
- Cross-feature импорт идёт через публичный `index.ts`; приватные файлы другого feature не импортируются.
- Типы внешних API валидируются на входе и преобразуются во внутреннюю модель.
- Побочный эффект изолируется в adapter; domain-функции детерминированы.

## Когда нужен ADR

ADR создаётся до реализации, если решение меняет границы модулей, хранилище, внешний provider, публичный контракт, модель безопасности, traceability, release gate или создаёт труднообратимую зависимость. В ADR фиксируются контекст, варианты, решение, последствия, риски и критерий пересмотра. Малые локальные рефакторинги ADR не требуют.

Шаблон: `docs/decisions/0000-template.md`. Принятый ADR не переписывается задним числом: новое решение получает следующий номер и ссылается на заменяемое.
